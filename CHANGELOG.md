# Changelog

- **Typed metric states, first step (B4): result schema 6 and a versioned result store.** `Metric` gains a `state` (`measured`, `unsupported`, `inapplicable`, `skipped`, `error` or `not_estimable`) and a `reason`. `value` is `None` exactly when the state is not `measured`, a non-empty reason is required whenever it is not, and a measured value must be finite (SQLite stores NaN as NULL and JSON writes it as null, so it would come back as a measured metric with no value). Nothing emits another state yet: every suite still writes measured values, and showing the other states in the report, CLI and dashboard comes next. `EvalRunResult.metric()` still returns `None` only for a metric the run did not emit; for one it emitted without a value it raises `MetricNotMeasuredError`, which carries the state and reason, and `metric_entry()` returns the `Metric` itself. Result artifacts move to schema 6. An older artifact migrates on read with every metric `measured`, because that is all the old shape could say: `value` was a required float, and a metric that could not be computed was left out. Each of the 346 metrics in the nine committed artifacts averages a non-empty sample. The SQLite store is now versioned in `PRAGMA user_version`, and opening an existing store upgrades it in place in one transaction. `metrics` is rebuilt, since SQLite cannot drop `NOT NULL` in place: `value` may be NULL, every existing row is copied with state `measured`, and a CHECK keeps a value present exactly when a row is measured. `records` gains `payload_schema`, the result schema a payload was serialised at; rows written before this keep NULL, because their writers did not record it. A new store is created at the latest version, and a store from a newer version is refused. On a copy of a real nine-run store all 357 metrics and 1,432 records came through unchanged. Code from before this change can still read and write an upgraded store, except a run holding a metric that was not measured, which it cannot read. In the API, `/runs/{id}/results` metrics carry `state` and `reason`, and `/runs/{id}/records` rows carry `payload_schema`.
- **Planted documents' source paths no longer name them to the system under test (B1, oracle fix).** Attack and canary documents used to get source paths like `__poison__/q001.md`, `__inject__/q005.md` and `__canary__/email-00.md`. The prompt prints each chunk's source, and every defense receives it on the chunk, so the generator was shown which passage was the attack, and a defense could have screened by reading one string. No shipped defense did. `tests/unit/pipeline/test_source_blind.py` now fails if one reads the source on its fixture contexts, under four labellings including numbered siblings. On `smoke-fake`, all 36 attack-trial prompts and 52 of the 54 privacy prompts carried such a label; now none does.
  - **Where they go now.** One of the corpus's own top-level directories that still holds documents after the ingest filters, picked by a seeded hash, under a name built from the document's own topic, e.g. `products/battery-life.md` beside the real `products/at-300-spec.md`. A planted name never repeats or shadows a corpus file's name, even one the filters dropped, and never pairs with one as `x` / `x-2`. When names collide, the document takes another window of its topic's words or a qualified name (`parental-leave-policy`) instead; a number is appended only when every such name is taken. Accented topics are folded to ASCII, and topics with no Latin words get neutral names.
  - **What changes for callers.** The suites track planted documents by `doc_id`. `POISON_SOURCE_PREFIX`, `INJECT_SOURCE_PREFIX` and `CANARY_SOURCE_PREFIX` are removed from `rag_crucible.attacks`, which breaks code that imported them. The three generators take keyword-only `corpus_sources` (where documents may go) and `avoid` (paths they must not take); left empty, documents are placed at the root. Targets, payloads and seeds are unchanged, but planted `doc_id`s change with their paths. There is no result-schema change and no change to clean prompts.
  - **What the numbers do.** Fake-provider results are identical in every metric and record, and in `spec_hash`: on `smoke-fake`, all 74 metrics and every record in all four suites match the previous code, so CI numbers do not move. Every published Qwen2.5-0.5B security and privacy number was measured with the path visible. Hiding only the canary path, by replacing it with a neutral hex name in `kb/`, moved privacy leakage under no defense from 5/27 to 10/27 in one run. All five changed probes went one way (exact McNemar *p* = 0.0625, not significant). The corpus-shaped scheme shipped here has not itself been measured on a real model. Those numbers are left as recorded, and the README and the three experiment pages that publish them now say so.
  - **What is still visible.** The prompt still prints each chunk's path, and a planted path is named from the target question, so it reads as a file about the question. Measured on the seeded corpus, with every question attacked twice: all 112 planted names share a content word with their question, and so do 47 of the 56 real documents that answer one, so the cue is weak but not zero. The planted text still carries the target id (`OWNED-q001`), the word "canary" inside canary secrets, and fixed poison boilerplate and headings. Replacing the path with an opaque per-chunk label is a separate change that will also change clean answers; the payload tells are A2's.
- **Breaking: the package, executable and environment variables are renamed (L2).** The import package `crucible` is now `rag_crucible`, and the FastAPI app moves from a top-level `api` package to `rag_crucible.api`. The executable `crucible` is now `rag-crucible`, and `CRUCIBLE_*` environment variables are now `RAG_CRUCIBLE_*` (the old names are no longer read). Why: a published package, `crucible-security`, ships the same top-level `crucible/` and the same `crucible` entry point, and installing both overwrote this project's files; uninstalling it then deleted them. The wheel now ships only `rag_crucible/`, and CI checks that. Unchanged on purpose, because they collide with nothing and renaming them would orphan existing data: the default result store `artifacts/crucible.db`, the Qdrant collection prefix `crucible_`, and the compose volume `crucible-data`. Also unchanged: the distribution name `rag-crucible`, and every committed run id and result directory. To upgrade: reinstall (`uv sync`) and rename any `CRUCIBLE_*` variables.
- **Stable attack-target sampling (A7) — changes which targets every security run attacks, and which clean-control questions it samples.** `select_targets` now ranks QA items by `sha256(seed, qid)` and takes the top *n*, instead of `random.Random(seed).sample` in file order. Reordering the QA file no longer changes the targets, an appended item displaces at most one, and a removed item replaces only itself. The same spec now attacks different targets and samples a different clean control than before, so the committed security experiments reproduce only on code at or before `477ef0c` (where the executable is still `crucible`). The run's `spec_hash` does not record the change. A store refuses only an identical `spec_hash`: runs recorded by older code hash differently, so their spec is accepted again and runs on the new sampler as a separate run. A spec submitted on code between `477ef0c` and this change is refused as a duplicate; pass `--force` to re-run it.
- **Stored specs round-trip (A5):** re-serialising a stored result writes its spec exactly as recorded, so it reproduces its own `spec_hash`. All nine committed artifacts do; before this, all nine drifted.
- **Dashboard:** `defense_clean_screen_rate` is shown under "What the defenses cost" instead of with attack success.
- **Versioned result artifacts (A8):** `EvalRunResult` gains `schema_version` and `run_id`, so a `results.json` identifies itself instead of depending on the directory it was written to; `rag-crucible eval` mints an id like the worker does. Stored results are read through `rag_crucible.eval.migrate`, which walks an older artifact up a registered migration chain and then validates strictly — a future version is refused rather than coerced, and a test fails if a version bump ships without its migration. The rule every migration follows: a field an older writer never recorded reads as `None`, never as a value, so `AttackRecord.own_marker`/`matched_markers`/`abstained` and the markers derived from them are now nullable and the security suite drops unrecorded trials from a metric's denominator rather than counting them as clean. One `SuiteStatus` alias replaces the literal that was spelled separately in the eval layer and the result store, where a status one side could produce was one the other rejected. Migration is deliberately read-only: re-serialising a historical result through today's `RunSpec` backdates options that did not exist when it ran and breaks its stored `spec_hash`, which is now guarded by a test over every committed artifact.
- **One-command submission + worker dual persistence:** `rag-crucible submit` now queues, atomically claims, executes, and waits for its own run by default, producing normalized SQLite data for the API/dashboard and the same portable JSON/Markdown/plot bundle as `rag-crucible eval` under `results/<spec-name>/<run-id>/`. It attaches to an identical active run left by queue-only/background execution, while completed duplicates still require `--force`. `--queue-only` preserves asynchronous submission for background-worker deployments. Report roots are environment-configurable and container reports live on the persistent artifact volume; forced reruns never overwrite prior exports.
- **Phase 6 — providers, store, dashboard, polish:** Cohere provider first-class (Embed v3 / Rerank 3.5 / Command, also usable as the faithfulness judge), OpenAI-compatible provider (embed + chat; rerank stays a capability error), shared retry wrapper (backoff + jitter) for hosted providers, Qdrant `VectorIndex` adapter with a `store: qdrant` build/load path (exercised via qdrant-client in-memory mode), Vite + React + TS dashboard (trade-off radar, rerank lift, attack-success-by-defense, leakage decomposition, latency, two-run diff), `cohere`/`openai`/`qdrant` extras, README how-to-plug-in-Cohere + add-a-provider, CI dashboard build, docker-compose dashboard + qdrant profile.
- **Phase 5 — privacy:** PII-canary seeding (synthetic emails/API-keys/phones in reserved test namespaces), extraction probes (direct/indirect/paraphrase), privacy suite measuring leakage decomposed into retrieval-exposure vs generation-leakage with a `pii_filter` ingestion-redaction defense (also a registered ingest filter), privacy report table + plot, threat-model privacy section. Measured: redaction holds exposure at 1.0 while driving generation leakage 0.185 → 0.00.
- **Phase 4 — security (the differentiator):** `attacks/` library (corpus-poisoning + indirect-prompt-injection document generators, deterministic `OWNED-{qid}` compliance tokens), security suite measuring poison/injection retrieval rate and attack success per defense, two query-time defenses (`injection_filter`, `prompt_isolation`) reported as variants, poisoned in-memory index reusing the warmed embedder, `docs/threat-model.md`, measured ASR-with/without-defenses in README. Lifted `qa` to a top-level module to break the eval↔attacks cycle.
- **Phase 3 — service (MVP complete):** SQLite result store doubling as job queue (atomic claims, spec-hash dedupe), evaluation worker with suite-level failure isolation, FastAPI API (submit/poll/results/records/cancel + live /query + health), provider warm-up before timing, bounded item concurrency in suites, `rag-crucible submit|worker|serve|runs`, Dockerfile + docker-compose (api + worker), CI image build.
- **Phase 2 — measurement:** retrieval suite (recall@k/nDCG@k/MRR) with explicit rerank-lift variants, faithfulness suite (sentence-claim entailment via swappable LLM/heuristic judge with committed judgment cache, citation correctness, answer accuracy), `rag-crucible eval` + reports (results.json, summary.md, plots), BEIR SciFact fetch script, measured results in README.
- **Phase 1 — core spine:** provider interface with `local` + `fake` implementations, ingestion (loaders/filters/chunkers), FAISS index, RAG pipeline with citations and per-stage timing, `crucible` CLI, seeded corpus + QA labels, tests + CI.
- **Phase 0 — design:** `docs/DESIGN.md` and `docs/architecture.md` written; MVP cut line confirmed after Phase 3.
